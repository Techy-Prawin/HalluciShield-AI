# 13 - Scan Orchestration

## Overview

Scan orchestration manages the lifecycle of a code analysis scan: from initiation through agent execution to completion and cleanup.

## Scan States

```
PENDING → SCANNING → COMPLETED
                  ↘ FAILED
```

| State | Description |
|-------|-------------|
| `PENDING` | Scan registered, not yet started |
| `SCANNING` | Agents executing analysis |
| `COMPLETED` | All agents finished successfully |
| `FAILED` | One or more agents failed |

## Scan Lifecycle

### 1. Scan Initiation

```
POST /api/orchestration/scan
```

**Request body**:
```json
{
  "repositoryId": "uuid",
  "workspacePath": "/optional/explicit/path"
}
```

**Backend processing** (`orchestration.router.ts`):
1. Generate `scanId` via `crypto.randomUUID()`
2. Resolve workspace:
   - If `body.workspacePath` provided: use it directly (legacy)
   - Else: look up `archive_path` from DB, materialize via `WorkspaceService.materializeScanWorkspace()`
   - Fallback: `WorkspaceService.runDir(scanId)`
3. Create a `ScanRecord` and persist its orchestration metadata in the `scans` table
4. Call `startScan()` asynchronously
5. Return `202 Accepted` with scanId

### 2. Agent Execution

`orchestration.service.ts` → `startScan()`:

1. Set status to `SCANNING`
2. Propagate `X-Request-ID` to AI engine calls
3. Call agents sequentially:
   ```
   POST http://ai-engine:8000/api/v1/hallucination/detect
   POST http://ai-engine:8000/api/v1/security/scan
   POST http://ai-engine:8000/api/v1/dependency/analyze
   ```
4. Each call includes `workspace_path` pointing to scan directory
5. Aggregate results into `ScanRecord`

### 3. Completion

On success:
- Set status to `COMPLETED`
- Store aggregated results (hallucination findings, vulnerabilities, dependencies)
- Set `completedAt` timestamp
- Auto-clean managed workspace if `managedWorkspace === true`

On failure:
- Set status to `FAILED`
- Store error message
- Auto-clean managed workspace if `managedWorkspace === true`

### 4. Status Query

```
GET /api/orchestration/status/:scanId
```

Returns current scan state, progress, and results (if completed).

### 5. Results Retrieval

```
GET /api/orchestration/results/:scanId
```

Returns full scan results including all agent findings.

## Workspace Materialization

When scanning without an explicit `workspacePath`:

1. Backend looks up `archive_path` from repository metadata
2. `WorkspaceService.materializeScanWorkspace(archivePath, scanId)`:
   - Cleans destination directory (idempotent)
   - Re-extracts from staged archive
   - Preserves zip-slip protection
3. Returns `workspacePath` for AI engine calls

## Request Tracing

Every scan gets a traceable request ID:
- Generated by `requestIdMiddleware`
- Propagated to AI engine via `X-Request-ID` header
- Logged with scanId for correlation

## Cleanup

After scan reaches terminal state:
- If `managedWorkspace === true`: `WorkspaceService.cleanupScanWorkspace(workspacePath)`
- Only cleans paths inside workspace root
- Best-effort: errors logged, not thrown

## Scan State Persistence

The backend keeps a process-local cache for fast polling and persists the complete
orchestration record in `scans.metadata` during production execution:

```typescript
const scans = new Map<string, ScanRecord>();
```

After a restart, status, stage results, and generated patch responses are reloaded
from PostgreSQL by scan ID. Set `PERSIST_SCAN_STATE=true` to enable the same behavior
in non-production local runs.

## Error Handling

- AI engine errors passed through un-mangled to client
- 4xx from AI engine: returned as-is
- 5xx from AI engine: returned with original error detail
- Network errors: scan marked as FAILED with error message
